## Assessment

**I would prioritize a correctness release before expanding the API or calling the remaining work
cosmetic.** The strongest findings are observable wrong results and broken history, not style issues:

| Priority | Finding | Evidence |
| --- | --- | --- |
| P1 | A snapshot-aware flush after TRUNCATE resurrects rows, including at the historical truncate snapshot. | Public-API reproduction; C01 fixed and pushed in `62058cc`. |
| P1 | Partial rewrite accepts active sources containing deleted rows and destroys their pre-delete history. | Public-API reproduction with real Parquet; C02 fixed and pushed in `db75f2b`. |
| P1 | Unknown bounds can make DuckDB return `MAX(id)=1` for actual rows `1,100`. ANALYZE does not repair it. | Public-API reproduction with real Parquet; C03 fixed and verified, see status below. |
| P1 | Column DDL on a MySQL table with inlined data can persist despite the operation failing. | Public-API operation with fault injection, C06. |
| P1 | Inlined reads can substitute NULL for an initial default or swallow DuckDB column-binding failures as empty results. | Focused read reproductions, C08/C09. |
| P1 | Replay comparison and timeout handling can hide defects behind a green report. | Focused comparator probes and control-flow review, H02-H05. |

This is not a dismissal of the implementation. It contains substantial upstream research, unusually
useful interoperability tests, and well-chosen public abstractions. The problem is that **local fixes
have outpaced enforcement of cross-cutting invariants**. Several features work independently but fail
when combined: compaction plus deletions, DDL plus inlining, ANALYZE plus concurrent writes, and optional
table reads inside a transaction.

The existing tests all pass. That is meaningful evidence of regression coverage, but not evidence that
the findings below are harmless. In particular, corpus identity control validates the harness against
DuckDB; it is not a blanket test of this catalog's write protocol or a downstream connector.

## Catalog Findings

### C01: Flush/TRUNCATE

**Status: FIXED and verified on 2026-09-05; release pending.**

Committed and pushed to `origin/main` in `62058cc` (`fix(flush): reject stale flushes after truncate`).

`ConflictMatrix.checkFlushedInlinedData` now rejects an intervening same-table `deleted_from_table`
as a non-retryable logical conflict. This covers existing TRUNCATE snapshot records without a metadata
encoding change or migration. It deliberately also rejects ordinary same-table deletes; file inserts
and deletions on other tables remain allowed. The snapshot-aware flush contract documents this behavior.

Upstream revalidation: DuckLake `d8a1881` checks flush versus `tables_deleted_inlined` in
`references/ducklake/src/storage/ducklake_transaction_state.cpp:258-262`; inlined deletes populate that
kind in `ducklake_transaction.cpp:984-985`. This extra matrix entry is an intentional stricter rule for
this library's TRUNCATE encoding, not a claim that upstream has the same conflict entry.

Regression: `TestJdbcDucklakeCatalogUpstreamFileShapesInterop.flushRejectsATruncateCommittedAfterMaterializationPreservingHistory`
materializes real Parquet before TRUNCATE on PostgreSQL, then verifies terminal rejection, unchanged
snapshot/file registration/stats/inlined rows, and stock-DuckDB current, truncate-snapshot, pre-truncate
value, and row-ID reads. `TestConflictMatrix.flushRowIsUpstreamPlusStricterEntries` checks both the new
same-table conflict and the unrelated-table allowance. Both rejection assertions failed before the
implementation fix because no exception was raised. The focused suites passed afterward (15 tests).

Full verification: `mise exec -- ./gradlew check --rerun-tasks --no-configuration-cache` passed with
290 catalog + 51 SLT + 33 replay tests (374 total, zero failures or skipped tests), detekt, and `checkAbi`.
The earlier evidence tables retain the original review's baseline counts. This fix does not close
C13's snapshot-less materialization gap, modify upstream engine internals, or repair already-damaged history.

**Original finding at the review baseline:**

**P1; API repro.** `J:3326-3329,3385-3390,3422-3424`; `Matrix:233-238`.

TRUNCATE end-snapshots inlined rows but records only `DeletedFromTable`. The snapshot-aware flush checks
intervening inlined insert/delete changes, not `tablesDeletedFrom`. A payload materialized before
TRUNCATE is therefore accepted afterward. Its backdated files lack the truncate deletions, and draining
the original inlined rows removes the end-snapshot evidence. Both current results and history change.

Record the inlined effect of TRUNCATE or conservatively conflict flush with intervening table deletes.
Add the sequential materialize/TRUNCATE/flush interleaving to the existing snapshot-aware flush tests.
This affects the new explicit-read-snapshot overload, not just deprecated compatibility paths.

### C02: Partial History

**Status: FIXED and verified on 2026-09-05; release pending.**

Committed and pushed to `origin/main` in `db75f2b` (`fix(compaction): reject partial rewrite sources that lose history`).

`assertPartialRewriteSourcesEligible` now rejects any selected source with non-NULL `partial_max`,
delete-file history (not just currently active delete files), or inlined deletions. All checks use the
write transaction's context and run before mutations on every attempt. Unsupported sources raise
`DucklakeInvalidOperationException` without retry and direct callers to ordinary `rewriteDataFiles`.
The existing newer-delete logical-conflict check is retained. The public contract now explicitly
requires delete-free sources and preservation of every source row.

Upstream revalidation: DuckLake `d8a1881` excludes delete-bearing and inlined-delete-bearing sources in
`references/ducklake/src/functions/ducklake_compaction_functions.cpp:281-285`, with an additional

`references/ducklake/src/storage/ducklake_metadata_manager.cpp:2125-2129`. The non-partial restriction
enforces this library's existing API contract; it is not a claim that upstream forbids every partial source.

The reused `dynamicTableExists` probe also needed namespace scoping: PostgreSQL now resolves through
`to_regclass` and its search path; MySQL checks the current database; DuckDB/Quack check the current
catalog/schema. Without this correction, an identically named table outside the current namespace
could turn an eligible rewrite into a missing-table failure.

Verification added seven tests:

  uses real Parquet and a tagged delete file, checks rejection without metadata changes, and verifies

- `TestJdbcDucklakeCatalogUpstreamFileShapesInterop.partialRewriteRejectsInlinedDeletesAndPreservesHistory`
  uses a DuckDB-written inlined file deletion and verifies unchanged current/history results and deletion metadata.
- `TestJdbcDucklakeCatalogRewriteDataFiles.partialRewriteRejectsPartialSources` checks the existing

- `partialRewriteIgnoresInlinedDeleteTablesOutsideTheSearchPath` in the interop suite,
  `partialRewriteIgnoresInlinedDeleteTablesInAnotherDatabase` in the MySQL smoke suite, and
  `partialRewriteIgnoresInlinedDeleteTablesInAnotherSchema` in the local-DuckDB smoke suite verify
  namespace isolation and successful eligible rewrites.
- `TestJdbcDucklakeCatalogOnQuackWrites.partialRewriteWithoutInlinedDeletesWorksOnQuack`
  checks the eligible path through remote transaction/query routing.

The three source-rejection regressions failed before the eligibility fix because no exception was

`mise exec -- ./gradlew check --rerun-tasks --no-configuration-cache` passed with 297 catalog + 51 SLT +
33 replay tests (381 total, zero failures or skipped tests), detekt, and `checkAbi`.

This change does not address C03/C04's statistics defects, C12's multi-output row-ID contract, ordinary

**Original finding at the review baseline:**

**P1; API repro.** `J:4728-4747,4787-4791`; `API:829-843`.

Partial rewrite accepts sources with deletions already visible at the caller's read snapshot. Its
documented output contains exactly the live source rows, but it physically removes source and delete

end-snapshotting rewrite when applying deletes. Test historical results before and after both variants.

### C03: Unknown Bounds

**Status: FIXED and verified on 2026-09-05; push and release pending.**

Committed locally in `f8f6eb8` (`fix(stats): preserve unknown bounds and complete file coverage`).

The count-aware accumulator distinguishes proven all-NULL contributions (`value_count`, which counts
NON-NULL values, is zero and both counts are known) from unavailable bounds on potentially non-NULL
data. Unknown bounds absorb later contributions in either order, and the first bound is validated
just like subsequent bounds. The existing two-argument merge/seed signatures remain available, but
without count evidence NULL bounds now mean unknown, never proof of an empty column.

Read aggregation and file-based rebuilds now share `aggregateFileColumnStats`: it LEFT JOINs from the
active file inventory and checks distinct per-column file coverage, including files with no statistics
rows at all. Missing rows in nonempty files invalidate counts and bounds; zero-row files are neutral.
Missing pre-ADD-COLUMN statistics do not prove NULL or any particular initial default, so they remain
unknown rather than allowing the newer file's extrema to exclude older default-filled values.

Incremental writes include existing global columns even when a new fragment omits their statistics.
An unsafe or one-sided global range is removed as a whole row, not persisted as NULL bounds. This is
important for mixed writers: upstream `FromGlobalStats` treats NULL/NULL as empty, whereas initialized
native inserts UPDATE existing rows rather than recreating missing ones. JVM inserts likewise do not
recreate missing global rows on initialized tables. First initialization checks that there are no
prior active files or inlined-table registrations. Explicit file-based rebuilds can restore rows once
coverage is complete. There is no full historical-file scan on each incremental insert.

Upstream references at `d8a1881`: `ducklake_stats.hpp:37-53` (`AnyValid`),
`ducklake_stats.cpp:76-99,129-181` (global reload and merge),
`ducklake_transaction.cpp:1191-1212` (non-NULL count encoding), and
`ducklake_metadata_manager.cpp:4464-4484` (initialized global UPDATE, not upsert), all under
`references/ducklake/src/include/storage` or `references/ducklake/src/storage` as appropriate.

Verification added 17 tests across `TestDucklakeStatTypes` and `TestJdbcDucklakeCatalogUnknownFileStats`:

- Unknown bounds, unknown counts, missing column rows, and completely statless files; both insertion
  orders and same-batch versus separate commits, followed by another bounded insert and ANALYZE.
- Stock-DuckDB MIN/MAX and scan results over real Parquet, including a native INSERT after global
  suppression; missing statistics cannot be revived into a new-only global bound.
- Non-NULL count versus NULL count semantics, malformed first bounds, unknown persisted seeds,
  all-NULL contributions, empty files, one-sided numeric globals, and NaN-bearing contributions.
- Initial defaults on pre-ADD-COLUMN files and restoration only after unknown files are retired and
  ANALYZE sees complete file statistics.
- NUL normalization before both initial and existing-row global publication, also closing C20.

The pre-fix focused run had 11 expected failures, including incorrect MAX results for absent bounds,
missing rows, and historical defaults. An old NaN assertion was corrected to stop treating NaN as
all-NULL, and the row-shape fixture now supplies statistics for both columns so its NaN-flag assertions
test complete coverage rather than expecting an unsafe row to survive an omission.

`mise exec -- ./gradlew check --rerun-tasks --no-configuration-cache` passed: 314 catalog + 51 SLT +
33 replay tests (398 total, zero failures or skipped tests), detekt, and `checkAbi` (7,705 classes).

Compatibility and scope limits:

- Suppression trades optimization for correctness. Even a persisted truly all-NULL global row lacks
  enough count evidence to distinguish it from unknown data during a later incremental merge; it may
  be suppressed until a complete rebuild. Missing per-file statistics are not synthesized from defaults.
- Native DuckDB `SET NOT NULL` can refuse a column with no global stats row instead of scanning it
  (`ducklake_table_entry.cpp:681-692`). The recovery test checks that refusal and subsequent success
  after complete statistics are restored. ANALYZE cannot restore bounds while coverage is still missing.
- Existing finite globals corrupted before this fix are not automatically repaired by an ordinary
  insert. A quiescent file-based rebuild removes unsafe globals and restores bounds only where
  coverage is complete; C04 subsequently replaces the live-inlined-row skip with suppression. Readers may
  need their metadata cache refreshed. Tests use fresh DuckDB sessions for this verification.
- C04's live-inlined-row rebuild gap is addressed separately below. C05's concurrent ANALYZE publication,
  C07's logical-type pruning comparisons, and R01's historical type selection remain open. This is not a claim that arbitrary
  native maintenance or previously cached statistics are made safe by the JVM fix.

**Original finding at the review baseline:**

**P1; API repro for absent bounds; focused repro for absent stat rows.**
`Stats:255-270`; `J:1391-1411,1616-1630,4511-4516,5125-5133`.

The bounds accumulator equates `(null,null)` with an all-NULL file. It has no value/null-count input to
justify that conclusion. A non-NULL file with unavailable bounds is ignored, leaving another file's
extrema as the purported table bounds. Separately, aggregation joins only existing stat rows, so an
active file with no stat row for a column contributes nothing rather than making statistics unknown.

The first case produced an incorrect DuckDB metadata-derived MAX through valid public write input;
ANALYZE reproduced the same error. The second was demonstrated at `getColumnStats`; its downstream
optimizer consequence was not separately executed. Pre-ADD-COLUMN files with initial defaults also
need conservative treatment rather than blanket omission.

Track whether a contribution is provably all NULL, potentially non-NULL, or unknown. Invalidate bounds
for unknown contributors and account for every relevant active file. Upstream's `AnyValid()` uses counts
and otherwise defaults conservatively (`references/ducklake/src/include/storage/ducklake_stats.hpp:45-52`).
Test both orders, one batch versus separate commits, missing rows, historical defaults, and ANALYZE.
The W-B8/R-D6 checkmarks currently overstate closure.

### C04: Mixed-Storage Stats

**Status: FIXED and verified on 2026-09-05; push and release pending.**

Both rewrite variants and ANALYZE now share a suppress-or-rebuild policy. If live inlined rows exist,
`recomputeTableColumnStats` removes every global column-stat row for the table instead of publishing
a file-only aggregate or retaining historical extrema. Gross row counts, file sizes, and the row-ID
allocator are preserved/recomputed independently. With no live inlined rows, the C03-aware file
aggregate can rebuild complete statistics; empty and deleted-only inline tables do not block it.

Detection runs on the operation's own transaction context, considers all registered schema versions
up to its schema ceiling, and uses half-open row visibility. Rewrites supply their schema version
directly because the new snapshot row has not been inserted yet. Missing registry/physical tables
are checked without raising an expected PostgreSQL error; unexpected query failures abort and roll
back. ANALYZE captures its snapshot/schema pair on that connection and also uses it for gross-inline
counting, addressing the ANALYZE portion of C14 without another pool borrow.

Upstream revalidation at `d8a1881`: `references/ducklake/src/storage/ducklake_transaction_state.cpp:716-790,793-928`
aggregates live inline values when it can. Its fallback avoids publishing the recomputed counters as
well as the new bounds. The JVM rewrite has already adjusted gross counts, so copying that fallback
as a skip would let stale extrema appear exact. Removing global rows uses C03's durable suppression
policy; initialized native and JVM inserts do not recreate them from new-only contributions.

Six tests in `TestJdbcDucklakeCatalogMixedStorageStatsInterop` cover:

- Real ordinary rewrite applying tagged deletes to Parquet extrema `-1000` and `1000`, while inline
  `-100`, `100`, and NULL remain. They check MIN/MAX, NULL predicates, row IDs, gross/live counts,
  file bytes, and unchanged historical reads. Later native inline and JVM file inserts preserve suppression.
- Real partial rewrite of delete-free sources with live rows only in an older inline schema and an
  empty latest version. The inline insert and schema change occur after materialization; detection
  must use the current attempt, not the caller's older read snapshot. Complete `id` statistics keep
  the MIN/MAX check independent of C03's missing-coverage behavior.
- ANALYZE removing deliberately stale globals, then restoring file statistics after inline rows end
  at the current snapshot; physically retained deleted rows still contribute to gross counts.
- Both rewrites and ANALYZE with a single-connection pool, including absent physical inline tables
  and an absent registry, followed by successful queries.
- Exclusion of future inline schema versions and future row begin snapshots using metadata fixtures.
- Rollback of both rewrite variants on an unexpected inline-column query failure, including source
  visibility, globals, counters, and scheduled-file metadata.

The first three regressions failed before the fix: stock DuckDB returned MIN/MAX `(1,1)` or `(1,2)`
instead of `(-100,100)`. Afterward, `mise exec -- ./gradlew check --rerun-tasks --no-configuration-cache`
passed with 320 catalog + 51 SLT + 33 replay tests (404 total, zero failures or skipped tests), detekt,
and `checkAbi`. New mixed-storage oracle scenarios use PostgreSQL; the full existing suite also checks
MySQL, local DuckDB, and Quack paths.

This is conservative suppression, not typed inline-value aggregation. C03's optimization and native
`SET NOT NULL` limitations still apply while global rows are absent. C05's concurrent ANALYZE publication,
C14's snapshot-conflict diagnostic borrowing, C15's public read-session probes, and ordinary rewrite's
inlined-delete concurrency limitation remain open. Existing reader-cache invalidation is unchanged.

**Original finding at the review baseline:**

**P1; source plus shape repro.** `J:4929-4942,1570-1580`; contrast `J:1450-1457`.

Both rewrite variants rebuild global column statistics solely from surviving file statistics even
while live inlined rows remain. ANALYZE explicitly avoids this mistake, but `netRewriteStats` does not.
Gross count still includes inlined rows, potentially making incomplete bounds appear exact. The
resulting metadata shape made DuckDB return MAX 1 while an inlined row held 100.

Fold transaction-consistent inlined statistics into the rebuild, or invalidate unavailable bounds so
DuckDB falls back to scanning. Simply retaining overly wide historical bounds is not sufficient: after
rewriting away deleted extrema, gross count can equal net count and DuckDB can treat those stale bounds
as exact. Add tests combining live inlined rows with a rewritten deleted extreme, as well as inlined
extrema and NULLs. Do not blindly copy ANALYZE's skip-only strategy or call its pool-backed helper from
inside a write transaction; see C14.

### C05: ANALYZE Publication

**P1; source.** `J:1437-1459,1484-1502,1621`.

ANALYZE captures snapshot S and computes counts, but publishes mutable global statistics outside the
snapshot conflict protocol. On PostgreSQL READ COMMITTED, a writer can commit an out-of-range value
between computation and publication. ANALYZE then overwrites its count and rebuilds bounds filtered
at old S. Too-tight bounds are not merely poor estimates: DuckDB also uses them to eliminate filters
or scans. The old tracker assertion that this can never leave count below live is incorrect.

Serialize publication with writers or use a shared conflict protocol; a repeatable read alone cannot
make stale publication safe. Add a barrier-controlled ANALYZE/INSERT test and check a filtered DuckDB
query, not just the stats table. The concurrent scenario remains source-verified, not runtime-reproduced.

### C06: MySQL Atomicity

**P1; API repro with injected failure.** `J:2546-2608,2650-2666`.

Column schema changes create a new physical inlined table inside the metadata transaction, after
metadata mutations and before snapshot publication. MySQL's non-temporary CREATE TABLE implicitly
commits. A later failure cannot roll back the prior column changes. The probe observed a failed DROP
persisting at a future snapshot ID, then becoming visible on an unrelated successful commit.

Until there is a safe physical-table preparation/publication protocol, reject affected MySQL operations
before mutations. Moving CREATE after metadata commit alone creates a missing-table visibility window
and is not an adequate fix. Test injected failures and snapshot collisions on an inlined MySQL table.
The old expiration-DROP atomicity fix is correct; this is a separate CREATE path.

### C07: Pruning Semantics

**P1; focused repro.** `Stats:125-127,329-334,386-388`; `J:5178-5184`.

Two valid-value cases can exclude files containing matching rows:

- FLOAT stats `0.1` and predicate bounds `0.10000000149011612` represent the same float32 value, but
  comparison as decimal spellings distinguishes them and can prune equality.
- TIME `24:00:00` is a valid DuckDB end-of-day value. The Java formatter normalizes it to midnight,
  causing a file containing it to be excluded for `>= 23:00:00`.

Normalize floating values to their declared binary precision. Represent end-of-day TIME explicitly,
or fail open by rejecting it as uncomparable rather than silently normalizing it. Add API-level pruning
tests against DuckDB's logical-type comparisons, not only comparator self-consistency tests.

### C08: Initial Defaults

**P1; focused read repro.** `J:2096-2100,2132-2134`; shared change-feed projection at `J:1990`.

After DuckDB inlines `(7)` into `t(id)` and adds `c INTEGER DEFAULT 42`, DuckDB returns `(7,42)` but
`readInlinedDataDecoded` projects `(7,NULL)` for the old schema version. The target column exposes
`initialDefault`, but projection keeps only requested IDs and emits unconditional NULL for absent
source columns. Preserving defaults during DDL did not make the read path apply them.

Resolve absent-column read values under the target snapshot's default/type metadata, without replacing
real stored NULLs. Test ADD COLUMN and subsequent default changes. The shared change-feed projection
has the same NULL behavior, but `API:378-393` explicitly promises NULL-filling there: default-aware
change feeds are a contract/parity decision requiring updated documentation and consumer coordination,
not simply an implementation violating that existing contract. Both are separate from exposing current
default expressions and dialects.

### C09: Empty-Read Errors

**P1; focused read repro.** `J:305-310,2156-2160,5451-5458`.

DuckDB has no useful SQLState for these errors. The fallback accepts any diagnostic containing
`ducklake_` and `not found`, including a missing-column binder error whose SQL excerpt names an
inlined table. Renaming a physical column under its unchanged catalog entry made decoded reads return
an empty list rather than raise corruption/query failure. The PostgreSQL regression exercises a
different, correctly classified SQLState branch.

Match the actual undefined-table diagnostic, not generic words or the echoed query. Extend the existing
physical-column mismatch regression to DuckDB and Quack. R-B5 is only partially resolved.

### C10: DDL Namespaces

**P1; source plus shape repro.** `J:2785-2792,2988-3000,3047-3069,3570-3579,3881-3886,3918-3930,4205-4206`.

Sequential schema/table/view CREATE does not reject already-active names. Table rename checks tables
but not views; column creation/addition/rename does not consistently enforce sibling uniqueness;
`addField` checks case-sensitively. The metadata schema has no matching uniqueness constraint to save
these operations, and retry-time name conflict detection does not catch sequential calls.

Duplicate active columns can prevent DuckDB loading a table; a table/view name collision can resolve
to the wrong relation. Use transaction-local, case-insensitive namespace checks for relation names and
sibling fields. Test sequential duplicate calls as well as races and case-only spellings. Existing
tests of concurrent CREATE are not substitutes for these checks.

### C11: Nested Arity

**P1; source plus shape repro.** `J:3894-3905,4215-4231`; `DucklakeTypeNames.kt:87-98`.

Recursive DROP now removes descendants correctly, but does not validate the surviving parent's
shape. Removing the only STRUCT field or a structural LIST/MAP child can leave an invalid tree.
`dropColumn` also accepts nested IDs. Without inlined-table DDL to fail incidentally, the invalid
metadata can commit. A childless STRUCT shape caused a DuckDB catalog-load internal error.

Validate post-mutation arity. Reject removal of required collection children and the last STRUCT
field, and constrain nested-field paths. Add empty-table tests so physical storage cannot accidentally
mask missing catalog validation. W-B4's dangling-descendant fix is sound but not the whole invariant.

### C12: Partial Row IDs

**P1; source.** `J:4732-4733`; `DucklakeDataFile.kt:161-172`; `API:838-843`.

Every partial-rewrite output is separately registered at the same smallest source row-ID start.
Unlike `FlushedInlinedFile`, `PartialMergedFile` has no per-output row-ID origin, and its contract
requires embedded snapshot IDs but not embedded row IDs. Two adjacent outputs without embedded row
IDs therefore expose overlapping fallback row-ID ranges.

Supply an origin per output, analogous to the recent flush correction. Require embedded IDs when
contiguity cannot be guaranteed. Test multiple actual output files and partition ranges. Ordinary
rewrite explicitly requires embedded row IDs, so the same fallback observation is not that API defect.

### C13: Legacy Guards

**P1; source; shipped compatibility limitation.** `J:3333-3353,3539-3541`; `API:538-540,585-600`.

Legacy flush has no materialization snapshot and drains all live rows at commit. An inlined insert
between file materialization and method entry is outside its conflict window and is lost. Deprecated
snapshot-aware overloads substitute a commit-time snapshot, so they cannot recover the missing read
boundary either. Deprecated DELETE/MERGE overloads similarly retain weaker read protection.

Deprecation does not make unsafe use impossible. Plan a versioned migration to explicit read snapshots,
correct the legacy flush safety promise, and test each retained overload's behavior. Do not silently
remove shipped APIs without checking consumers. The main guard also explicitly excludes concurrent
inlined file deletions (`API:815-817`); retain that as an operational limitation until covered.

### C14: Pool Reentrancy

**Status: PARTIALLY FIXED by C04 on 2026-09-05.** ANALYZE's snapshot, inlined discovery, gross counts,
and live-row probes now use its owned connection; the one-connection regression passes. The separate
`snapshotConflictFromAnotherConnection` path still borrows while holding the failed transaction's
connection and remains open. Do not close C14 as a whole.

**Original finding at the review baseline:**

**P2; API repro for ANALYZE; source for collision diagnostics.** `J:1443-1456,1493,1522-1526,2509,2718,2729-2735`.

ANALYZE owns a connection but calls helpers using the pool-backed `dsl`. With a configured pool size
of one, even an empty table waits 30 seconds and fails. Snapshot-conflict reporting also borrows while
the failed transaction still owns a connection. At pool exhaustion, diagnostics can replace a retryable
conflict with a terminal acquisition failure; larger pools reduce, but do not remove, this cycle.

Keep operation reads on their supplied context. Release the failed connection before optional
diagnostics, or construct the retryable exception without another borrow. Test a one-connection pool,
including a loser racing a separate catalog instance. Raising the minimum pool size is not a full fix.

### C15: Aborted Sessions

**P2; API repro.** `J:227-248,305-310,1910-1919,1556-1559`.

An absent optional inlined-delete table is normal. Suppressing PostgreSQL `42P01` returns `false`, but
inside `readSession` the transaction stays aborted and the next query fails with `25P02`. This also
breaks `getLiveRowCount` within one session callback. Outside a session, separate autocommit statements
hide the problem.

Use transaction-safe absence handling, such as a non-error existence query with suitable race handling
or a savepoint around the probe. Do not roll back the entire session and silently change its snapshot.
Combine missing-table tests with the read-session tests.

### C16: Value Decoding

**P2; focused repro.** `Values:310-348,409,419-421`.

The interval clock regex accepts at most two hour digits and searches for a substring: valid DuckDB
`100:00:00` decodes to zero hours, and `123:45:06.007` loses the leading digit. Unrecognized text can
silently become a zero interval; accepted `1 ms` is classified as minutes after suffix stripping.
Separately, a quoted VARCHAR value literally containing `CAST('hello' AS VARCHAR)` becomes `hello`
because the upstream-workaround unwrapping is applied after token quoting information is discarded.

Consume the complete interval with checked arithmetic and explicit units. Preserve token provenance
and unwrap only actual unquoted CAST expressions. Add large/signed interval and literal-CAST-string
round trips. These are residual R-D4 bugs, not unsupported logical types.

### C17: MySQL Rendering

**P2; source.** `InlineDDL:84-124`.

Inlined-table CREATE always double-quotes names and uses DuckDB type spellings unless the backend is
PostgreSQL. Default MySQL mode does not accept those identifier quotes; types such as `UBIGINT`,
`HUGEINT`, unbounded `VARCHAR`, and nested types are not a MySQL mapping. jOOQ cannot repair raw SQL.

Provide real backend rendering or reject unsupported inlining DDL before mutation. Test default SQL
mode and actual supported type families. Fixing quoting alone exposes C06 rather than fixing atomicity.

### C18: Partition Validation

**P2; source plus shape repro; caller-input dependent.** `J:4379-4380,4404-4410`; old W-N1.

Partition ID and partition values are persisted independently. Missing or incomplete values under a
partition ID can cause upstream equality pruning to exclude the file. No explicit contract delegates
this structural validation to the caller, but the demonstrated failure requires inconsistent supplied
metadata; this is not evidence that valid partition payloads are corrupted.

Validate ID ownership and applicable key coverage, including the distinction between an absent key and
a present SQL NULL. Add missing, extra, foreign-spec, and valid NULL-value tests. This merits more than
a cosmetic nit because invalid metadata can silently change query results.

### C19: Sorted Renames

**P2; source plus shape repro.** `J:3918-3930`.

Column rename leaves stored sort expressions referring to the old name. After a sorted `x` is renamed
to `z`, DuckDB INSERT planning can fail because `x` no longer resolves. Upstream rewrites the expression
references (`references/ducklake/src/storage/ducklake_table_entry.cpp:184-201`).

Version and rewrite dependent sort metadata, or reject the operation until supported. Test subsequent
DuckDB INSERT and historical sort metadata, not only the renamed column row.

### C20: NUL Statistics

**Status: FIXED and verified with C03 on 2026-09-05; push and release pending.**

The shared aggregate normalizes bounds with `statText` before comparison/publication, including
persisted-global merges. `TestJdbcDucklakeCatalogUnknownFileStats.nulBoundsAreNormalizedBeforeGlobalInsertAndUpdate`
covers NUL-bearing bounds on first insertion and after an existing known row, a later known insert,
and ANALYZE. Unsafe global rows stay absent. See C03 for full-suite verification.

**Original finding at the review baseline:**

**P2; source.** `J:4441-4444,4550-4566,5125-5133,5336-5337`.

Per-file bounds pass through NUL sanitization, but the global accumulator consumes the original strings.
A VARCHAR bound containing NUL can therefore still reach global INSERT/UPDATE and make PostgreSQL
reject the transaction, contrary to the advertised behavior.

Normalize before aggregation and persistence, using C03's unknown-bound semantics. Test both creating
and updating a global statistics row with a NUL-containing fragment.

### C21: Empty Projection

**P2; focused read repro.** `J:2123-2125`.

An empty inlined column projection returns zero rows even when rows exist. This silently discards
cardinality for count-only or virtual-column-only consumers. Select a dummy/system column and return
one empty value list per row, or explicitly reject the projection if that is the intended contract.
Upstream handles COUNT(*) by reading `row_id` rather than pretending the table is empty.

### C22: Path Namespaces

**P2; source.** `J:745-750`; `API:137-147`.

The legacy per-table reference API mixes table-relative data paths and catalog-relative scheduled paths
while its documentation tells callers to resolve relative entries against the table directory. An
upstream scheduled path such as `main/t/a.parquet` can become `root/main/t/main/t/a.parquet` in an orphan
sweep's known set. The new catalog-wide API correctly separates these cases.

Deprecate the old API for orphan detection, correct its contract, or normalize its output. Verify
connector adoption and add a relative scheduled-path test. No physical deletion was attempted in this
review; the risk is a downstream consumer following the current resolution contract.

### C23: Diagnostic Secrets

**P2; source.** `J:205-208,285,320`; `CatalogExceptions.kt:122-123`.

Configured JDBC URLs are emitted verbatim at INFO and included in diagnostic exceptions. Valid URLs
may embed password/token parameters. Separate password properties avoid this particular leak, but the
library neither rejects URL credentials nor redacts them.

Use a redacted diagnostic URL consistently for logs and exceptions. Test synthetic credentials in
query parameters and user-info. No actual secrets were extracted or recorded during this review.

### C24: Initialization Errors

**P2; source.** `J:2519-2525,2616,2289-2295`.

Reads classify an unbootstrapped database as `DucklakeCatalogNotInitializedException`, while CREATE can
produce generic `DucklakeException`, and file-write preflight can expose raw `DataAccessException`.
An empty snapshot table is classified differently too. Q-1's status text says writes have the typed
initialization behavior, but the write path does not apply that guard.

Use a consistent initialization boundary and classification. Extend the initialization tests to CREATE
and file commits, enabling downstream adapters to map the error predictably.

## Replay Findings

### H01: Cleanup Ownership

**P1; source.** `Oracle:30-31,149-154`.

A supplied `testDirRoot` becomes the directory deleted on close, not a parent under which the oracle
creates an owned temporary directory. Its pre-existing contents are therefore at risk. The use of
`File.deleteRecursively()` also permits traversal through directory symlinks in the reviewed Kotlin
implementation. This was verified by source inspection, not by running destructive cleanup.

Create an owned child and delete without following links. Test that pre-existing parent files and an
external symlink target survive. Document ownership explicitly even if callers currently pass only
disposable roots.

### H02: Golden Accuracy

**P1; focused repro.** `Comparator:48-65,245-269,303-327`.

The comparator discards JDBC types and result metadata, then guesses semantics from strings and SLT
letters. It accepted BIGINT `10000000001` against expected `10000000000`; values above double's exact
integer range can collapse too. VARCHAR `true` can satisfy expected `1`. A `query I` returning two
columns can pass a two-cell golden because query arity is not enforced; empty results lose arity entirely.

Carry column count and SQL types alongside rows. Compare integral/decimal values exactly under their
logical type, restrict Boolean coercion to Boolean columns, and validate ordinary-query arity. Add
negative live-JDBC tests; already-rendered happy-path strings cannot test information that was discarded.

### H03: Mirror Collisions

**P1; focused repro.** `Driver:504-519`.

Live comparison maps NULL/empty values into textual golden tokens and joins columns with an unescaped
separator. SQL NULL and literal `NULL` compare equal; empty string and literal `(empty)` do too.
Rows `["a\u0001b","c"]` and `["a","b\u0001c"]` serialize identically. These are avoidable collisions
because the engine interface already distinguishes nullable cells.

Compare structured nullable rows, preserving arity and using lexicographic row ordering where order is
intentionally ignored. Keep SLT golden conventions out of live-vs-live equality.

### H04: Timeout Accounting

**P1; source.** `Runner:69-90,112-116`; replay identity test `TestIdentityControl.kt:88-95`.

A timed-out file is replaced by an empty-outcome skip, losing any earlier failures. It is neither a
reported failure nor a crash, so sufficient passes elsewhere can leave the suite green. Timeout-as-skip
is an explicitly documented policy (`Runner:25-31`); losing earlier failures is a defect regardless of
that policy. The worker is abandoned, not terminated. Fresh drivers still share the same engine and
metadata-rewriter objects, so an old worker resuming later can act on a subsequent file's connection.

For verification runs, change policy to fail on timeout and preserve partial outcomes. Do not reuse
shared engine state until the worker terminates; abort the run or use process isolation if cancellation
is unreliable. Test a failure-then-timeout and a latch-controlled worker resuming after the next file begins.

### H05: Mirror Coverage

**P1 for engine conformance; source.** `Driver:388-392,482-487`; `ReplayReadEngine.kt:19-22`.

An engine whose `accepts()` always returns false can produce all oracle passes and zero engine queries
without an engine-skip count. Attachment gates, transaction gates, and the mirror cap are similarly
invisible in pass totals. The interface says rejection is an engine skip, but the outcome stays Pass.

Separate oracle passes from mirror attempts/passes/skips and record reasons. Require meaningful mirror
coverage in downstream conformance suites. Keep oracle-only identity control valid, but label it as
such. Test an always-rejecting fake engine and a file never successfully attached to that engine.

### H06: Parsing Budgets

**P2; source.** `Parser:291-298`; `Runner:62-63`.

A tiny numeric-loop header can eagerly allocate an effectively unbounded list of iteration values.
Parsing occurs before the watchdog and crash wrapper. Deep nested input also lacks a nesting budget.
This is a resource boundary for the published parser, not merely a slow SQL query. The enormous
allocation was not executed during review.

Use bounded/lazy ranges, constrain nesting and expansion, and put parsing inside failure isolation.
Add safe tests that reject huge ranges without allocating them. Trusted checked-in corpora reduce the
exposure but do not make the public parser bounded.

### H07: Attachment State

**P2; focused state repro and source.** `Driver:133-198`.

After lake A, a second lake B disables mirroring, but a third C can reconnect because
`!engineConnected` permits it. This contradicts disabling for the rest of the file. Quoted DETACH is
not recognized. Some detach/pinned-attach state changes happen before SQL succeeds, so an expected
statement failure can silently disable valid coverage.

Track successfully executed attachment transitions, with a persistent unsupported-multi-lake state.
Test A/B/C, quoted aliases, failed DETACH/ATTACH, snapshot pins, and replacement. S-B3 is incomplete.

### H08: Error Boundaries

**P2; source.** `Driver:308-319`.

Oracle SQL and `engine.connect()` share one SQLException catch. A successful ATTACH marked
`statement error` followed by an adapter connection exception can be counted as the expected SQL
failure. Determine the oracle statement outcome first; classify adapter setup failures separately.
Add a fake engine that throws on connect after successful oracle execution.

### H09: Conversion Sentinels

**P2; focused repro.** `Comparator:54-62`.

Every JDBC conversion exception becomes the ordinary string `<jdbc-unreadable>`. A broad regex golden
can accept it, and labels can hash repeated failures rather than values. TIME `24:00:00` demonstrated
this path. Propagate conversion failure or record an explicit, narrowly classified driver skip; never
compare or hash a failure sentinel. Test throwing getters, regex goldens, and labels.

### H10: Timestamp Precision

**P2; focused JDBC repro.** `Comparator:198-202`; `TestIdentityControl.kt:37-38`.

The driver returned nanoseconds `123456789` for TIMESTAMP_NS, but the formatter divides by 1,000 and
renders microseconds. The curated skip currently blames JDBC for this loss. Shared formatting can also
hide an engine's precision loss. Preserve the fractional nanoseconds, trim only trailing zeros, and
test pre-epoch and nanosecond-distinct values before reevaluating the exclusion.

### H11: Conditional Parity

**P2; source and focused condition check.** `Conditions:24`; `Expander:119-121`; `Driver:259-260`.

The implementation negates a conjunction for `skipif`; upstream applies skip policy per term. At
`i=0`, `skipif i=0&&i=1` executes here but skips upstream. See
`references/duckdb/test/sqlite/sqllogic_command.cpp:260-273`. Apply skip/only policy per term and test
mixed true/false terms for both directives. Ordinary `onlyif` conjunction tests miss this distinction.

### H12: Truncated Loops

**P2; focused parser repro.** `Parser:170-172,279-285`.

EOF and a matched `endloop` are not distinguished. An unterminated loop becomes a runnable normal
loop instead of an unsupported/malformed record, allowing a truncated test to pass. Propagate
terminator status and test missing inner and outer terminators. Upstream reports `Missing endloop!`.

### H13: Iterator Shadowing

**P2; focused expansion repro.** `Expander:106-107`; `Driver:233-235`.

A name-keyed binding map replaces an outer iterator when a nested loop reuses its name. Upstream's
ordered outermost-first replacement consumes the outer placeholder first. Preserve an ordered binding
stack or explicitly reject unsupported shadowing. Existing distinct-name nesting tests do not cover it.

### H14: DML Results

**P2; focused JDBC repro.** `Driver:395-409`.

All recognized DML is sent through `executeUpdate()`. Valid `INSERT ... RETURNING` under a query
directive mutates the table and then fails because it returns rows. Support both result sets and
affected-row counts in a single-execution path. Simply replacing every call with `execute()` is not
sufficient: the current code documents DuckDB JDBC returning update count `-1` for ordinary DML on that
path. Never re-execute a mutation to recover its count. Test INSERT/UPDATE/DELETE RETURNING alongside
ordinary affected-row counts, comments, and CTE-prefixed statements.

### H15: Runtime Formatting

**P2; focused Java 17 repro.** `FloatText:22-24,59-65`.

Formatting relies on Java 19+ shortest-digit conversion while the artifacts target Java 17. On Java 17,
`1e23` renders as `9.999999999999999e+22`, and Float.MIN_NORMAL as `1.17549435e-38`, differing from DuckDB.
This is additional to the already-documented subnormal differences (`1.4e-45` versus `1e-45`,
`4.9e-324` versus `5e-324`). Use runtime-independent conversion or state and enforce a higher runtime
requirement. Add actual Java 17 renderer tests; classfile compatibility does not prove identical behavior.

### H16: Golden Substitution

**P2; source.** `Driver:469`.

Inline golden cells are replaced outright with their environment-substituted form. Upstream accepts
either the raw cell or its substituted form; raw regex handling also differs. A query producing the
literal text `${FOO}` can therefore fail after `FOO=bar` despite a valid raw golden. Retain raw
expectations and compare substituted alternatives rather than preprocessing them destructively.

## Strengths

- **S01: A valuable shared boundary.** The engine-agnostic catalog avoids duplicating subtle metadata rules
  in Trino and Doris. Separating a dependency-light SLT format library from execution is also sound.
- **S02: Real oracle testing.** Tests frequently write through one implementation and read with stock DuckDB,
  covering defaults, quoted aliases, recursive columns, cached name maps, row identity, and time travel.
  These tests are materially stronger than asserting the library can read its own writes.
- **S03: Good local protocol primitives.** Half-open snapshot visibility is centralized; typed write changes,
  conflict exceptions, per-table schema-version tracking, and explicit snapshot-aware APIs make the
  intended rules discoverable. Consolidated delete guards consider `partial_max`, not just begin time.
- **S04: Meaningful earlier fixes.** Name maps use the file-ID allocator, column version replacement preserves
  defaults, schema drop checks views/macros, database time is used, NULL required row-ID starts fail,
  and delete-file snapshot filtering is documented independently of `partial_max`.
- **S05: Improved backend discipline.** Quack has explicit server transaction hooks and mixed-path rollback
  tests. PostgreSQL read-session tests cover destructive metadata changes and nesting. Backend conflict
  classifiers and rollback-cause preservation are substantially better than the old review describes.
- **S06: Maintenance separation.** Catalog-wide reference enumeration includes dropped-but-unexpired owners
  and separates scheduled path roots. Expiration preserves latest and uses surviving-snapshot tests;
  physical file cleanup remains a distinct age-gated responsibility.
- **S07: Useful library ergonomics.** Wire-format records, real serializer tests, typed exceptions, published
  fixtures, clear coordinates, signing, and explicit Java 17 deployment motivation are good investments.
- **S08: Traceable decisions.** Most complicated code explains its upstream reference and interoperability
  reason. This made independent review possible, even where the parity claims need correction.

The 5,629-line catalog class is not a bug merely because it is large. The concrete concern is that a
helper can silently switch from a transaction DSL context to the pool, or rebuild statistics without
considering inlined rows, while appearing locally reusable. The duplicate policy implementations are
more dangerous than repeated syntax. C04 and C14 are direct examples.

For N07, I would not start with a sweeping repository rewrite. First capture the failing invariants, then
extract only boundaries that make them harder to violate: transaction-scoped metadata access,
statistics aggregation with explicit completeness, and inlined row projection/materialization.
Keep a single public facade if it remains convenient. Avoid replacing one large class with many thin
delegators that still share ambiguous connection and snapshot state.

Other quality work worth scheduling:

- **Q01: Public API stability.** Add compatibility snapshots or an equivalent binary/API checker, plus explicit API review
  for published changes. The existing task called `checkAbi` checks bytecode floors, not ABI stability.
- **C03/C09/H09: Narrow fallbacks.** Make error classification and safe fallback deliberately narrow. Unknown statistics should fail open
  for pruning; unexpected query failures should not become empty data; test conversion errors should

- **N17: Backend capabilities.** Maintain a backend-by-operation/type capability matrix. A backend smoke test does not justify parity

  data models omit necessary information. Preserve the reason for intentional differences.
- **Q03: Lint baseline hygiene.** Reduce stale detekt baseline entries as code changes, rather than treating the baseline as proof of

## Residual Risks

These concerns were not promoted to verified runtime failures:

- **R01: Historical type selection.** `loadColumnTypes` reads all historical versions into an unordered `toMap()` (`J:5544-5556`). An old type
  could win after type evolution. Use snapshot-specific selection and test backend ordering effects.
- **R02: Conflict-history retention.** Snapshot conflict checks read retained changes without proving the intervening history is complete
  (`J:5266-5274`). Define retention obligations for long-lived plans/materializations and retries.
- **R03: Quack rollback recovery.** Quack suppresses wrapped rollback errors (`QuackWrappedMetadataQuery.kt:116-124`). Fault-inject
  transport failures and prove a returned pooled connection has no surviving server transaction.
- **R04: Isolation failure handling.** `readSession` treats isolation-setting SQLExceptions as unsupported functionality (`J:252-258`).
  Distinguish a known driver limitation from a failure to establish the promised consistency.
- **R05: Unknown DDL changes.** Unknown change kinds conflict with data writes but permit DDL (`Matrix:61-74`). That is defensible
  for a known bare inlined-insert compatibility case, not necessarily arbitrary future schema changes.
- **R06: Flush payload completeness.** Flush validates existing-file delete coverage, but not complete coverage of all inlined data before
  draining it (`J:3434-3453,3502-3512`). State the payload completeness obligation and test omissions.
- **R07: Change-feed identity.** Deletion records omit mapping/file identity information (`DucklakeChangeFeedDeletion.kt:60-80`).
  Verify named-file mappings after rename and embedded row-ID compaction with a real connector.
- **R08: Historical count estimates.** Live-row count estimates can overcount partial insertions as well as undercount consolidated
  deletes (`J:1541-1545`); describing them only as lower bounds is misleading.
- **R09: Catalog scalability.** Narrow change-feed windows still fetch substantial table history (`J:564-572`), and inlined reads
  materialize complete lists. No large-catalog latency, memory, query-plan, or pool-contention benchmark
  was run. Avoid performance claims based solely on the functional suite.
- **R10: Physical cleanup recovery.** Post-commit physical-table DROP failures are logged after registration metadata has been removed
  (`J:989-999`). There is no clear retry inventory for leaked tables. Add failure-path and sparse-retained-
  snapshot maintenance tests.
- **R11: Planning/cleanup lifetime.** `readSession` protects metadata consistency while its callback runs; it is not a lease preventing
  physical cleanup after planning. Consumers need a clear retention/grace contract.
- **R12: Replay isolation.** Replay is not a sandbox. Corpus SQL can use DuckDB filesystem/network capabilities, golden paths can
  point outside the checkout, regex matching can consume unbounded time, and result lists are unbounded.
  Untrusted corpora require disposable, credential-restricted isolation and adapters that reject writes.

### Broader Roadmap

These are grouped workstreams, not additional claim IDs:

1. **Stop demonstrated corruption/wrong results.** C01 and C02 are pushed; C03 and C04 are fixed and verified. Land failing regressions and focused fixes for
   C06; address C05 statistics publication, C07-C12 reads/DDL/history, and unsafe
   materialization entry points. Refuse unsupported cases rather than accepting corrupt metadata.
2. **Make verification trustworthy.** Fix H01-H05 and H09 before using pass totals as a conformance
   argument. Preserve result types/shape, separate engine coverage, and make timeouts fail visibly.
3. **Test the intersections.** Add pool-size-one, PostgreSQL optional-table-in-session, MySQL inlined
   DDL rollback, mixed inlined/Parquet rewrite, sorted rename, and historical partial-file tests
   (C14, C15, C06, C04, C19, C02/C12).
4. **Close contracts and adoption gaps.** Validate names/partitions/type shape, redact diagnostics,
   reconcile the tracker, publish capabilities, and verify downstream use of the safer APIs
   (C10/C18/C11, C23, N27, N17, N26).
5. **Strengthen delivery, then simplify.** Gate exact-SHA publication, enforce version agreement and
   Java runtime compatibility, add API compatibility checks, and extract the narrow invariant-owning
   components identified above (B02/B03/B01, Q01, N07). Treat harmless numbering/comment nits as the last tranche.

For a correctness finding, closure should mean a regression that fails before the fix, passes afterward,
and checks the externally observable result or atomicity invariant. For history-sensitive operations,
also check unchanged earlier snapshots. For backend failures, run the regression on that backend.
For harness findings, include intentionally wrong results that must fail. A new checkbox or a green
unchanged corpus replay alone is not sufficient closure.

**Bottom line:** keep the architecture and the oracle-driven testing approach. Tighten invariants,
transaction context ownership, and the credibility of verification. The project's strengths make these
issues tractable, but the remaining work includes real correctness defects, not just open nits.
